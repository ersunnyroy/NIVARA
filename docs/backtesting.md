# Backtesting

## BACKTEST vs PAPER vs LIVE

NIVARA keeps three kinds of results apart and labels each one. None of them places real orders.

| Mode | What it is | Where | Label |
|---|---|---|---|
| **BACKTEST** | Strategy simulated over a historical date range with the daily backtester | `app/backtesting/`, `/api/backtests` | Banner: "BACKTEST PERFORMANCE — simulated on historical data. Past simulated results do not guarantee future returns. Judge the out-of-sample TEST split, not the training split." |
| **Historical replay** | The live scanner re-run for past sessions with point-in-time data (`job replay`) | `recommendation_runs.trigger = "replay"` | Track record origin `historical_replay`, reported separately from `live` |
| **PAPER** | Simulated orders placed by the user (or the auto-following model portfolio), filled on the next session's official EOD bar | `app/paper/engine.py`, `/api/paper` | "Paper trading simulates fills on official EOD bars. No real orders are ever placed." |
| **LIVE** | (a) Recommendations generated by scheduled/manual scans and tracked forward on new data (`origin = live`); (b) the user's real trades, entered manually into `live` portfolios | `/api/recommendations/track-record`, `/api/portfolios` | Track-record note: "This is the model's paper track record, not live trading performance." |

The live recommendation track record is itself a simulation on EOD bars (see
[architecture.md](architecture.md#recommendation-outcome-tracking)); only the user's own `live` portfolio reflects
real executions.

## Engine

`app/backtesting/engine.py::Backtester` is a daily, event-driven simulator. It calls the same
`app/analytics/evaluate.py::evaluate` as the live scanner and the same `app/recommendations/outcomes.py::simulate`
as the live track record, so a backtest measures what the live system would have produced on daily bars.

For each session `t` (NIFTY 50 trading dates within the range):

1. Settle positions whose simulated exit date is ≤ `t` (proceeds minus sell charges).
2. Mark open positions to market at the close on `t`; record equity, cash and position count.
3. Every 5 sessions, recompute sector ranking and (if `regime_aware`) the market regime from index data ≤ `t`.
   In `BEARISH`/`STRONG BEARISH` regimes max positions is divided by 3; no new entries in `STRONG BEARISH`.
4. Build the universe from data ≤ `t`; compute cross-sectional relative strength; evaluate candidates.
5. Take the top `top_n` candidates (by score) for free slots; simulate the trade forward from `t + 1`; size it;
   deduct cash and buy charges.

At the end, positions still open are closed at the last close ("end of backtest").

### Strategies (`STRATEGIES`)

| Strategy | Pre-filter | Entry plan |
|---|---|---|
| `combined` | Close above 50-EMA | Full evaluation; requires action `BUY` and score ≥ `min_score` |
| `ranking` | Close above 50-EMA | Full evaluation; any non-rejected setup, ranked by score |
| `breakout` | Close above prior 20-day high with volume ≥ 1.5× its 20-day average | Full evaluation; `BUY` and score ≥ `min_score` |
| `momentum` | Close above 50-EMA and 63-session return > 10% | Full evaluation; `BUY` and score ≥ `min_score` |
| `mean_reversion` | Close above 200-EMA and RSI(2) < 10 | Fixed plan: entry 98–100.3% of close, stop close − 2×ATR, T1 max(20-EMA, close + 1×ATR), T2 close + 3×ATR, max 10 sessions |

## Look-ahead prevention

From the engine docstring:

1. Signals for session t are computed from bars with date ≤ t only (`evaluate` asserts this and raises
   `LookAheadError` otherwise).
2. Orders are placed after t's close and can only fill from session t+1 (entry-window rules in
   `recommendations.outcomes.simulate`, identical to the live track record).
3. The tradable universe on day t is chosen by trailing 20-session traded value measured on data ≤ t (no use of
   today's index membership → reduces survivorship bias; delisted stocks remain in the data for the sessions they
   traded).
4. Cross-sectional relative strength, sector strength and market regime are recomputed from data ≤ t.
5. Whether a position is still open on day t is decided by its simulated exit date ≤ t (observable on t).
6. Fundamentals, news and F&O are excluded by default (their point-in-time history is incomplete); excluded
   components are reported, and the score is normalised over available components.

Supporting guarantees elsewhere: indicators are causal (tested by `test_compute_all_no_lookahead`), swing pivots
need confirming bars to the right before they exist, and `test_future_data_cannot_change_past_decisions` checks
that appending future bars does not change earlier decisions.

## Survivorship mitigation

- The daily universe is the `universe_size` (default 250) most traded stocks by trailing 20-session traded value
  that pass the price (₹20) and traded-value (₹5 crore) filters and have at least 210 prior sessions — not the
  current NIFTY 500 list.
- Stocks that stopped trading remain in the stored data for the sessions they traded, if those sessions were
  ingested.
- Limitation: `execute_backtest` loads stocks that have a bar on the start date (falling back to any stock with
  bars after it) and whose current `series` is `EQ`. Stocks that listed after the start date are therefore not
  included when the start date has data.

## Fills, slippage, liquidity and charges

| Aspect | Rule |
|---|---|
| Entry | `simulate()`: within 3 sessions from t+1; at the open if inside the entry zone, at `entry_high` if it opens above and trades down into it, at the open if it gaps below the zone but above the stop; an open at/below the stop invalidates the trade |
| Exit | Stop checked before targets on the same bar; gaps through the stop fill at the open; stop moves to the trailing level after T1; full exit at T2; time exit at `holding_max` |
| Slippage | `slippage_bps` (default 10) added to the entry price and subtracted from the exit price |
| Position size | floor(equity × `risk_pct` ÷ risk per share), risk per share at least 0.5% of entry; capped at `max_position_pct` (20%) of equity |
| Liquidity cap | Quantity ≤ 2% (`max_volume_participation`) of the 20-session average volume up to t |
| Cash | Skipped if quantity × entry + buy charges exceeds cash |
| Charges | Delivery charges from the stored charge schedules for each fill date (brokerage, STT, exchange, SEBI, stamp, GST, DP) |
| Income tax | Not deducted from the equity curve (depends on the user's annual position); stated in the warnings |

## Train / validation / test splits

Sessions in the range are split chronologically by count: 60% train, 20% validation, 20% test (boundaries stored
in `backtests.splits`). Each trade is labelled by its signal date. Metrics are reported for `overall`, `train`,
`validation` and `test`. The API banner asks users to judge the test split.

## Metrics

Per split (`_segment_metrics`): start/end date and equity, return %, CAGR, max drawdown %, Sharpe and Sortino
(daily returns annualised with √252; only with ≥ 60 daily returns), number of trades, win rate, profit factor,
expectancy (mean net P&L per trade), average holding sessions, total charges. Fewer than 30 trades adds the note
"Fewer than 30 trades — statistics are not reliable."

## Limitations

- Prices are back-adjusted for splits/bonuses using factors known today; this rescales pre-event prices
  (ratios/indicators unchanged) and can marginally affect absolute-price filters (engine docstring).
- Fundamentals, news and F&O components are excluded, so backtest scores are normalised over technical, momentum,
  volume, relative strength, sector and risk/reward only — not identical to live scores.
- The backtest regime uses NIFTY, Bank NIFTY, India VIX and sector participation only (no breadth or flows), and is
  refreshed every 5 sessions.
- Daily bars only: intraday order of events is unknown beyond the conservative stop-first rule.
- The position size uses the simulated fill price; cash is reserved on the signal date and positions are valued at
  the entry price until the entry date.
- `params` accepted through the API: `capital`, `risk_pct`, `max_positions`, `top_n`, `slippage_bps`,
  `universe_size`, `min_score`. Other engine parameters (`max_position_pct`, `max_volume_participation`, `split`,
  `regime_aware`, price/turnover filters) use defaults. Scoring weights, risk limits and exclusions come from the
  current admin configuration. The `universe` field is stored but not used.
- Indicator warm-up: data is loaded from 430 days before the start date; a range needs at least 40 sessions.
- Results depend on how much history has been ingested (`job backfill`).

## How to run

### API

```bash
# create (queued on Celery when a worker responds, otherwise run in-process)
curl -X POST http://localhost:8000/api/backtests \
  -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" \
  -d '{"name":"combined 2025-26","strategy":"combined","start_date":"2025-10-01","end_date":"2026-09-30",
       "params":{"capital":1000000,"risk_pct":1,"slippage_bps":10}}'
# poll
curl -H "Authorization: Bearer $TOKEN" http://localhost:8000/api/backtests/<id>
```

`$TOKEN` is the `access_token` returned by `POST /api/auth/login`. A failed run is stored with `status = "failed"` and the error message,
and the exception is logged. The frontend's Backtesting page uses the same
endpoints.

### Command line

There is no dedicated CLI subcommand. Run the service functions directly (from `backend/`):

```bash
.venv/bin/python -c "
from datetime import date
from app.core.db import session_scope
from app.backtesting.service import create_backtest, execute_backtest
with session_scope() as db:
    bt = create_backtest(db, 1, 'cli run', 'combined', date(2025, 10, 1), date(2026, 9, 30), {})
    print(execute_backtest(db, bt.id))
"
```

The second argument is the owning user id (the API lists only the caller's backtests). A Celery worker can also
run it: task `nivara.backtest` with the backtest id.

### Historical replay of the live scanner

```bash
.venv/bin/python -m app.cli job replay start=2026-06-01 end=2026-09-30 every=5
```

Re-runs breadth, regime and the scanner for each stored session (every 5th here) using only data available at
that session, tags runs `replay`, skips sessions already replayed, then updates outcomes. Replayed
recommendations appear in the track record as `historical_replay`.
